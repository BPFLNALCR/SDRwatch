# Quickstart: Validate the Repository Inventory Feature

## Purpose

Use this guide to validate that the future `docs/PROJECT_INVENTORY.md` implementation accurately reflects the current repository state.

## Prerequisites

- Repository checked out locally.
- Python available in the active environment.
- Optional: an existing `sdrwatch.db` file if you want to validate the web UI's read-only behavior.
- Optional: Raspberry Pi with RTL-SDR hardware if you want to validate deployment claims directly.

## Validation References

- Contract: [contracts/project-inventory-contract.md](./contracts/project-inventory-contract.md)
- Data model: [data-model.md](./data-model.md)
- Plan: [plan.md](./plan.md)

## Scenario 1: Verify canonical entry points from a workstation

1. From the repository root, run:

```bash
python sdrwatch-control.py --help
python sdrwatch-web.py --help
python -m sdrwatch.cli --list-profiles
python query-sdrwatch.py --help
```

2. Confirm the implemented inventory document identifies:
   - `python -m sdrwatch.cli` as the canonical scanner entry point.
   - `sdrwatch-control.py` as the controller/API entry point.
   - `sdrwatch-web.py` as the primary web entry point.
   - `sdrwatch.py` and installer-created web shims as compatibility paths.

**Expected outcome**: The commands succeed without SDR hardware, and the document's entry-point section matches the observed behavior.

## Scenario 2: Verify no-hardware validation claims

1. Run the current automated tests:

```bash
pytest tests/test_detection_diagnostics.py tests/test_extent_hysteresis.py tests/test_segment_splitting.py
```

2. Optionally, if you have an existing database file, start the web app against it:

```bash
python sdrwatch-web.py --db sdrwatch.db --host 127.0.0.1 --port 8080
```

3. Confirm the implemented inventory document explains:
   - Which tests run without hardware.
   - That the web app can still expose read-only or waiting-state behavior without live SDR access.
   - That actual scanning and controller device discovery remain hardware-dependent.

**Expected outcome**: The document separates workstation-safe workflows from hardware-required workflows without overpromising live scan capability.

## Scenario 3: Verify installer and generated service-file claims

1. Inspect the install and uninstall scripts:

```bash
rg "/etc/sdrwatch.env|sdrwatch-control.service|sdrwatch-web.service|/opt/sdrwatch|/var/lib/sdrwatch|/run/sdrwatch-control" install-sdrwatch.sh uninstall-sdrwatch.sh
```

2. Confirm the implemented inventory document states that:
   - Service files are generated by `install-sdrwatch.sh`.
   - `/etc/sdrwatch.env` is generated during install.
   - uninstall preserves the database/state directory while removing runtime and service artifacts.

**Expected outcome**: The document accurately distinguishes committed scripts from generated deployment assets.

## Scenario 4: Optional Raspberry Pi deployment check

1. On a Raspberry Pi with RTL-SDR hardware, run:

```bash
SDRWATCH_AUTO_YES=1 ./install-sdrwatch.sh
sudo systemctl status sdrwatch-control
sudo systemctl status sdrwatch-web
sudo journalctl -u sdrwatch-control -n 20
sudo journalctl -u sdrwatch-web -n 20
```

2. Confirm the implemented inventory document's Raspberry Pi workflow section matches the installed services, env file, and runtime directories.

**Expected outcome**: The document's deployment guidance matches the installer's generated artifacts and service names.

## Completion Criteria

- Every section required by the contract is present in the implemented document.
- The document correctly distinguishes committed, installer-generated, runtime-generated, and missing assets.
- The no-hardware and Raspberry Pi workflow sections reflect the current repository and installer behavior.
- No implementation guidance in the document implies code rewrites beyond the inventory itself.
